Design rule

Nothing in the sale path may require a network hop beyond the shop switch. If a feature cannot work with the router unplugged from the world, it is not part of the sale path.

02 What makes this shop hard

A hardware shop and an agro-chemical shop have almost opposite inventory problems, and this business is both. Most off-the-shelf POS systems handle one and fail the other. The data model has to serve both without becoming two systems.

2.1 The hardware side: quantity is not a whole number

  • Cut-to-size sales. Three and a half metres of armoured cable off a 100 m roll. Eleven feet of angle iron. Quantity must be NUMERIC, never INTEGER, all the way through the ledger. Getting this wrong is unrecoverable later.
  • Purchase unit ≠ stocking unit ≠ selling unit. Screws arrive in a box of ten packets, are stocked as packets, and are sold as singles. One product, three units, live conversion between them.
  • Bulk breaking. Opening a carton is a real stock event that must be recorded, not an implicit side effect of a sale.
  • Almost nothing is barcoded. Search by name, by local name, and by short code must be fast enough to use with a customer waiting. Internal barcode labels are generated in-house for the items worth labelling.
  • Prices are negotiated. Counter staff discount. That is the trade, not an abuse to be blocked — but it needs a floor derived from cost and a ceiling derived from role.
  • Contractors buy on credit. Masons and builders run accounts and settle later. Receivables are a first-class part of the system, not an add-on.

2.2 The agro-chemical side: stock has a death date

  • Batch and expiry are mandatory. Herbicides, fungicides, treated seed and veterinary products all carry a manufacturer batch and an expiry date. Losing that link is both a commercial and a safety failure.
  • Picking is FEFO, not FIFO. First expiry out, which is not the same as first in. The picking rule is a property of the product, not a global setting.
  • Expired stock must become unsellable automatically at midnight, not by someone remembering.
  • Regulated product data. EPA registration number, hazard band, active ingredient and concentration, PPE guidance, re-entry interval. Some of it belongs on the receipt.
  • Restricted sales may need a buyer register — who bought what, when, and how much.
  • Demand is seasonal. A reorder point computed from a flat trailing average will under-stock every planting season and over-stock every dry one.
The unifying move

These two worlds converge if every unit of stock in the system belongs to a lot. Agro-chemicals get a real manufacturer batch with a real expiry. Hardware gets a lot generated automatically at goods-receipt, with a null expiry. One mechanism, one costing rule, one picking engine — and expiry simply stops applying where it is null.

03 Deployment topology

One machine holds the application and the database. Tills are browsers on the same switch, each paired with a small local agent that owns the peripherals. Nothing in the diagram below crosses the shop's front door.

3.1 Why the till is a browser and not a desktop app

A packaged desktop app would put printing in-process and remove the agent entirely. It would also mean shipping a new binary to every till for every change. Splitting the concern keeps the fast-moving part — the selling UI — behind a browser refresh, and confines the slow-moving part — driver quirks, ESC/POS byte encoding — to an agent that changes perhaps twice a year.

05 The stock ledger

This is the single most consequential decision in the system, so it comes before the module map.

Stock quantity is never updated in place. There is no UPDATE product SET qty = qty - 1 anywhere in the codebase. Every change to on-hand stock is an immutable, signed row in stock_movement, and the current balance is a derived value maintained by a database trigger.

Core ledger schema
-- Every on-hand quantity in the system belongs to a lot.
-- Agro-chemicals carry a real manufacturer batch; hardware gets one
-- generated at goods-receipt with a NULL expiry.
CREATE TABLE stock_lot (
  id          BIGSERIAL PRIMARY KEY,
  branch_id   BIGINT        NOT NULL REFERENCES branch(id),
  product_id  BIGINT        NOT NULL REFERENCES product(id),
  lot_code    TEXT          NOT NULL,
  expires_on  DATE,                          -- NULL = does not expire
  received_on DATE          NOT NULL,
  unit_cost   NUMERIC(14,4) NOT NULL,        -- GHS, per BASE uom
  status      TEXT          NOT NULL DEFAULT 'AVAILABLE',
                            -- AVAILABLE | QUARANTINED | EXPIRED | WRITTEN_OFF
  UNIQUE (branch_id, product_id, lot_code)
);
CREATE INDEX ON stock_lot (branch_id, product_id, expires_on NULLS LAST);

-- Append-only. Never UPDATE. Never DELETE. A mistake is corrected by
-- posting a compensating movement, which is itself part of the record.
CREATE TABLE stock_movement (
  id            BIGSERIAL     PRIMARY KEY,
  branch_id     BIGINT        NOT NULL REFERENCES branch(id),
  lot_id        BIGINT        NOT NULL REFERENCES stock_lot(id),
  movement_type TEXT          NOT NULL,
  qty_base      NUMERIC(16,4) NOT NULL,   -- signed, in the product's BASE uom
  unit_cost     NUMERIC(14,4) NOT NULL,
  source_type   TEXT          NOT NULL,   -- SALE | GRN | ADJUSTMENT | ...
  source_id     BIGINT,
  reason_code   TEXT,                     -- required for adjustments
  occurred_at   TIMESTAMPTZ   NOT NULL DEFAULT now(),
  created_by    BIGINT        NOT NULL REFERENCES app_user(id),
  CONSTRAINT qty_nonzero CHECK (qty_base <> 0)
);
CREATE INDEX ON stock_movement (branch_id, lot_id, occurred_at);
CREATE INDEX ON stock_movement (source_type, source_id);

-- Derived. The balance row is created with the lot, at zero, and thereafter
-- only ever UPDATEd by an AFTER INSERT trigger on stock_movement. See the
-- verified note below for why it must not be an INSERT ... ON CONFLICT.
CREATE TABLE stock_balance (
  branch_id  BIGINT        NOT NULL,
  lot_id     BIGINT        NOT NULL,
  qty_base   NUMERIC(16,4) NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ   NOT NULL DEFAULT now(),
  PRIMARY KEY (branch_id, lot_id),
  CONSTRAINT qty_never_negative CHECK (qty_base >= 0)
);
Verified the hard way — do not implement this with ON CONFLICT

The obvious way to write the balance trigger is a single INSERT ... ON CONFLICT (branch_id, lot_id) DO UPDATE SET qty_base = stock_balance.qty_base + EXCLUDED.qty_base. It does not work, and it fails on every sale.

PostgreSQL evaluates CHECK constraints against the proposed tuple before the arbiter index is consulted and the DO UPDATE path is taken. A movement of −3.5 against a lot holding 96.5 therefore trips qty_never_negative on the proposed row (−3.5) and never reaches the update that would have produced 93.

The working design creates the balance row at zero when the lot is created, so the movement trigger is a pure UPDATE. That also removes an insert race, and the row lock the UPDATE takes is precisely what serialises two tills racing for the last unit.

5.2 Picking rule

Which lot a sale draws from is a property of the product, not a global setting. Agro-chemicals use FEFO so the stock closest to expiry moves first; hardware uses FIFO so cost flows in receipt order; a handful of items are picked manually because the cashier can see which pile is which.

Picking, in the domain layer
sealed interface PickingRule {
    data object Fefo   : PickingRule   // agro-chemicals: nearest expiry first
    data object Fifo   : PickingRule   // hardware: oldest receipt first
    data object Manual : PickingRule   // cashier names the lot
}

fun List<StockLot>.pickFor(rule: PickingRule): List<StockLot> =
    filter { it.status == LotStatus.AVAILABLE }
        .let { available ->
            when (rule) {
                PickingRule.Fefo   -> available.sortedWith(
                        compareBy(nullsLast()) { it.expiresOn })
                PickingRule.Fifo   -> available.sortedBy { it.receivedOn }
                PickingRule.Manual -> available
            }
        }
Non-obvious consequence

Because cost lives on the lot and issue cost is the lot's cost, margin reporting is automatically correct per sale line without maintaining separate cost layers. But it also means a lot's cost can never be edited after movements exist against it. Correcting a mis-keyed purchase price requires a compensating adjustment pair, not an UPDATE. Build that correction screen in Phase 1 or storekeepers will invent worse workarounds.

06 Catalog, categories and units

6.1 Adding a category must never be a migration

The requirement is that new product categories can be added freely. The trap is that a genuinely new category usually brings genuinely new fields with it — a cable has conductor size and core count; a herbicide has active ingredient, concentration and an EPA registration number. If those fields are columns, every new category is a schema change and a deploy.

Categories are therefore an ltree hierarchy, and each category declares the attributes its products carry. Product attribute values live in a single indexed JSONB column, validated at write time against the declarations inherited down the tree path.

Category and attribute schema
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE category (
  id        BIGSERIAL PRIMARY KEY,
  parent_id BIGINT REFERENCES category(id),
  code      TEXT   NOT NULL UNIQUE,
  name      TEXT   NOT NULL,
  path      LTREE  NOT NULL,          -- e.g. agro.herbicide.selective
  kind      TEXT   NOT NULL DEFAULT 'GENERAL'  -- GENERAL | AGROCHEMICAL
);
CREATE INDEX ON category USING GIST (path);

-- Declaring a category's fields is data entry, not DDL.
CREATE TABLE category_attribute (
  id          BIGSERIAL PRIMARY KEY,
  category_id BIGINT NOT NULL REFERENCES category(id) ON DELETE CASCADE,
  key         TEXT   NOT NULL,
  label       TEXT   NOT NULL,
  data_type   TEXT   NOT NULL,        -- TEXT | NUMBER | BOOL | DATE | ENUM
  enum_values TEXT[],
  unit        TEXT,                   -- 'mm²', 'g/L', 'days'
  required    BOOLEAN NOT NULL DEFAULT false,
  sort_order  INT     NOT NULL DEFAULT 0,
  UNIQUE (category_id, key)
);

ALTER TABLE product ADD COLUMN attributes JSONB NOT NULL DEFAULT '{}';
CREATE INDEX ON product USING GIN (attributes jsonb_path_ops);

A category inherits every attribute declared above it on its path, so agro.herbicide.selective picks up the hazard band and EPA number declared once on agro. The product form is generated from the resolved declaration set; the same set drives filtering and the columns offered in reports.

Why JSONB over EAV

A classic entity-attribute-value table gives referential tidiness and costs a join per attribute plus a pivot for every listing screen. JSONB with a GIN index gives single-row reads, indexed containment queries, and a document that maps straight onto the API payload. The tradeoff is that validation moves into the application — which is why the declarations table exists rather than letting the JSONB be free-form.

6.2 Units of measure

Each product has exactly one base unit, and the ledger speaks only in base units. Every other unit is a conversion factor onto it. Purchase and sale both convert at the edges.

Unit conversion
CREATE TABLE product_uom (
  id         BIGSERIAL PRIMARY KEY,
  product_id BIGINT NOT NULL REFERENCES product(id) ON DELETE CASCADE,
  uom_id     BIGINT NOT NULL REFERENCES uom(id),
  factor     NUMERIC(16,6) NOT NULL,  -- base units contained in one of these
  is_base    BOOLEAN NOT NULL DEFAULT false,
  sellable   BOOLEAN NOT NULL DEFAULT true,
  purchasable BOOLEAN NOT NULL DEFAULT true,
  barcode    TEXT,
  UNIQUE (product_id, uom_id),
  CONSTRAINT factor_positive CHECK (factor > 0)
);
-- Exactly one base unit per product.
CREATE UNIQUE INDEX ON product_uom (product_id) WHERE is_base;

6.3 Regulated product fields

Products in a category of kind AGROCHEMICAL carry the fields a regulated product needs: EPA registration number, WHO hazard band, active ingredient and concentration, PPE guidance, re-entry interval, and whether the buyer must be recorded. The hazard band drives the colour coding used throughout the UI and on the printed receipt.

These are category attributes declared on the agro root, not a table of their own. The first design gave them typed columns on a supplementary profile row, and that row was never written by anything — no field on the create request, no service that saved one — so the buyer-record flag read false for every product and the licence control could never fire. Both tests covering it built a profile through the repository, which no production path did: green in CI, dead at the counter. V15 retired the table and moved the declarations to §6.1's mechanism, which validates on write, inherits down the path, and is reachable from the catalogue screen.

A category's kind is inherited rather than chosen: a GENERAL category under the agro root is refused. Its products would inherit these fields — and be sold with no expiry to enforce, since batch tracking is decided by the product's own category.

08 Selling

8.1 Sale lifecycle

DRAFT → HELD → COMPLETED, then optionally PARTIALLY_RETURNED, RETURNED or VOIDED. Held sales matter more than they look. A customer who leaves to fetch money from a mobile-money agent is routine, and their basket must survive on the server, not in browser memory, so any till can recall it.

8.3 Idempotent completion

The till generates a UUID when the operator presses Pay and sends it as an Idempotency-Key header. The server records it against the resulting sale inside the same transaction. A retried request — double click, impatient operator, a switch that dropped a frame — returns the original sale rather than deducting stock a second time.

Completion guard
@Transactional
fun complete(cmd: CompleteSaleCommand, key: IdempotencyKey): SaleResult {
    idempotencyRepo.findBySaleKey(key)?.let {
        return SaleResult.Replayed(saleRepo.getById(it.saleId))
    }

    val sale = draftRepo.getById(cmd.draftId).also { it.assertOpen() }
    val allocations = picker.allocate(sale.lines)      // FEFO / FIFO per product
    inventory.postIssues(allocations, sale.id)         // CHECK constraint guards oversell
    payments.record(sale, cmd.tenders)
    val document = billing.issue(sale)

    idempotencyRepo.save(IdempotencyRecord(key, sale.id))
    events.publish(SaleCompleted(sale.id, sale.branchId, sale.lineProductIds()))
    return SaleResult.Completed(sale, document)
}

8.4 Cedi rounding

Line totals compute to two decimals. The payable total rounds to the nearest 5 pesewas, because small coins are scarce and the difference otherwise gets absorbed silently by whoever is at the counter. The adjustment is stored on the sale as rounding_adjustment so the day's cash reconciles exactly. The increment is configuration — set it to 0.01 to disable.

8.5 Takings

There is no cash drawer in this shop, so there is no session to open against a counted float and nothing to reconcile at the end of the day. A sale records its payments and the till that rang it up; the takings report derives the day's figures from those payments, split by till and tender method.

The shrinkage control a cash session would have given is not available here, and nothing else replaces it. What remains is the stock take (§7.4), which catches shrinkage in goods rather than in cash, and the discount and void registers, which catch it at the point it is authorised. If a drawer is ever introduced, the session model is worth rebuilding then — it was removed because the hardware is absent, not because it was the wrong idea.

10 Printing

The server never emits ESC/POS bytes. It emits a print document — a structured description of what should appear — and the agent on the till turns that into bytes for the specific printer attached to it. Swapping an 80 mm Epson for a 58 mm Xprinter changes agent configuration and nothing else.

11.1 Fighting alert fatigue

An alerting system that cries daily gets ignored, and then the one that mattered gets ignored too. Three mechanisms, all in the schema: 

CREATE TABLE alert (
  id              BIGSERIAL PRIMARY KEY,
  rule_id         BIGINT      NOT NULL REFERENCES alert_rule(id),
  dedupe_key      TEXT        NOT NULL,   -- e.g. 'LOW_STOCK:branch1:product482'
  severity        TEXT        NOT NULL,
  title           TEXT        NOT NULL,
  body            TEXT        NOT NULL,
  subject_type    TEXT, subject_id BIGINT,
  raised_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  acknowledged_at TIMESTAMPTZ, acknowledged_by BIGINT,
  resolved_at     TIMESTAMPTZ,
  snoozed_until   TIMESTAMPTZ
);

-- At most ONE open alert per condition. Re-raising while it is still
-- open is a no-op, not a new row and not a new notification.
CREATE UNIQUE INDEX ON alert (dedupe_key) WHERE resolved_at IS NULL;

Alerts also auto-resolve: restocking above the reorder point closes the low-stock alert without anyone clicking anything. And snoozed_until lets the owner say "I know, the order is coming Thursday" without disabling the rule.

11.2 Reorder points

Recomputed nightly from a trailing 90-day window: 

reorder_point = ceil(avg_daily_usage × lead_time_days × safety_factor)
              + safety_stock

Every term is overridable per product, because the computed answer is wrong for anything seasonal. Agro-chemical categories additionally carry a per-month seasonal multiplier so the planting-season figure is not derived from dry-season sales. Flag any product where the computed and manual figures diverge sharply — that divergence is usually information.

11.3 Channels, given no internet

  • In-app notification centre — always works, the primary channel.
  • Dashboard badges — counts by severity on the home screen.
  • Printed morning briefing — a thermal slip at open of business: what expired overnight, what fell below reorder, yesterday's variance, overdue accounts. In a shop where the owner is on the floor rather than at a screen, this is the channel that actually gets read.
  • SMS — optional, queue-and-forward, critical severity only, drains whenever a connection exists. Never awaited.

Permissions are checked, not roles — roles are bundles of permissions, so the owner can build "senior cashier" without a code change. Supervisor override is a PIN entered at the till by someone holding the permission; the override is recorded with both identities, the reason, and the value before and after.

The audit log is append-only and covers price changes, cost visibility, voids, refunds, stock adjustments, override use, credit-limit changes, and role assignment. Because the whole system sits on one machine in a shop, physical access is the real threat model: full-disk encryption on the server, no shared logins, screen lock on the tills, and the database not listening on anything but the LAN interface.

14 Survivability

The system's largest single risk

"Local server only" means the shop's entire stock position, price history and receivables ledger live on one machine, in one building. A failed SSD, a surge, a flood or a burglary is not a bad day — without the measures below it is the end of the business's records. This section is not optional hardening; it is a functional requirement.

Backup and recovery

The verification row is the one that is usually skipped and the one that matters most. An unverified backup is a belief, not a backup. Because the restore drill is automated and its result feeds the alert engine, a silent failure surfaces as a Critical alert on the dashboard and on the morning slip within hours instead of being discovered on the day it is needed.

14.1 Degradation ladder

"Server down means trading stops" is the honest cost of the single-server decision. It is acceptable only because the manual fallback is designed and rehearsed rather than improvised. A warm standby machine restoring last night's dump is a modest addition if that cost turns out to bite.

17.1 Open questions

  1. ADR-001 — Kotlin or Java 21. Decided by who maintains this in three years, not by language merits.
  2. How many tills at go-live, and is the server a dedicated mini-PC or does it double as a till? Dedicated is strongly preferred.
  3. Does the shop already have a product list in any digital form, or is Phase 7 a full manual keying exercise?
  4. Restricted agro-chemical buyer register — required by the shop's licence, or a value-add? This changes whether it can be skipped under time pressure.
  5. Delivery — does the shop deliver cement and rods with its own vehicle? If so, delivery notes need a driver, a vehicle and a signature capture, which is a small module not currently scoped.
  6. Existing receivables — do contractor balances need migrating in as opening balances at cutover?
